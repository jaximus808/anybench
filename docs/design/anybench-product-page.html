Why correctness comes first

The benchmark that skips the work

Velocitty 1.3.0 shipped automated throughput comparisons against Ghostty, and the numbers said it was faster. Mitchell Hashimoto read the source and replied: your read loop overwrites a 64 KiB ring. Everything older is discarded unparsed per tick. You're faster because you're not actually terminal emulating. What the benchmark really measured was how fast the terminal could throw output away.

What that benchmark checked

  • Bytes in per second
  • Nothing about whether those bytes ended up on screen

What a Anybench kit checks

  • Every terminal gets the same byte stream on identical computers
  • After each run, the final screen and the full scrollback are compared with a reference parser, cell by cell
  • A run that doesn't match gets no speed score
  • The kit builds a version that drops chunks of output and confirms the gate catches it

Under the hood

How Anybench works

Inside Anybench is the eval factory: agents that decide how to test a harness and write the kit that does it. Naïve's compute runs that kit, and the results are what customers buy. Everything from here down is the detail, using Tandem as the worked example. The same steps apply to any software.

Station 3

What the agents decide: the eval kit

You aren't buying the kit. It's the agents' work: their decisions about how your harness should be tested, written down as plain files you can read and edit. For Tandem it's about six files. Because it's saved, the same test can run again on next week's version of your harness.

adapter

How to run it

harness.yaml plus run.sh: how to install the harness, run it on one task in one folder, and what to collect afterwards.

tasks

What to ask it

A starting repo plus instruction.md for each task. Some come from our suite, some come from your question, and some are made by reverting old commits in your repo.

requirements

How it's scored

Measured requirements (hidden tests, API latency, time, cost) and reviewed ones (code quality against a written rubric, scored by a separate review model that quotes its evidence). Weights combine them into one score. Scoring runs on a fresh computer.

stand-in

Who plays the human

For harnesses with an approval step: a reviewer that approves or rejects proposals. Its policy is one of the settings you compare.

proof

Why you can trust it

The results of the five checks below, saved with the kit so anyone can rerun them.

Station 4

The five checks every kit must pass

This is what makes "agents write the tests" safe. An agent can write a bad grader, but it can't make a bad grader pass all five of these.

CheckPasses whenWhat it catches
oracleThe reference solution scores 100% on every taskGraders that are broken or too strict
do-lessA version that does nothing, or skips part of the real work, fails the correctness gateTests that pass by default, and benchmarks that reward skipping work (the Velocitty problem)
smokeYour harness finishes a tiny task on the real cloud imageInstall, auth and path problems, before you spend real money
planted regressionA deliberately worse copy of your setup scores lower (for example, a CLAUDE.md that says "skip the tests," or a 3-turn cap)An eval that can't tell setups apart
baseline sanityKnown baselines reproduce their published numbers within rangeA broken benchmark setup: wrong build flags, a throttled computer, a missing warm-up

The adapter, concretely

What the factory writes for each kind of harness

A harness is just a command that takes a task and a folder and exits when it's done. Everything else is our side. Pick a harness to see its adapter.

eval/harness.yaml 
name: tandem
source: github.com/jaximus808/tandem@main
install: |
  npm i -g @anthropic-ai/claude-code
  npx -y @jaximus/tandem-mcp --help >/dev/null   # warm the npx cache in the snapshot
run: eval/run.sh {task} {workspace}
vary:                                            # each value is one setup to compare
  WORKERS: [1, 3, 5]
  APPROVER: [auto, llm-reviewer]
human_in_loop: tandem-approvals                  # we supply the stand-in
collect: [out/*.jsonl, out/tandem/]               # transcripts + the board's SQLite file
secrets: [ANTHROPIC_API_KEY]                     # injected at run time, never in the kit
eval/run.sh 
#!/usr/bin/env bash
# One trial. The runner calls: run.sh <instruction.md> <workspace>
set -euo pipefail
TASK="$1"; WS="$2"; N="${WORKERS:-3}"; OUT="${EVAL_OUT:-/eval/out}"
CC="claude --dangerously-skip-permissions --output-format stream-json --verbose"  # disposable VM
cd "$WS"

# 1. A fresh Tandem for this trial only, data kept with the results
npx -y @jaximus/tandem-mcp setup --project --no-claude-md --no-open --data-dir "$OUT/tandem"
npx -y @jaximus/tandem-mcp init --write              # pin this repo to a new canvas

# 2. The human stand-in (ours): approves or rejects what lands as proposed
eval-approver --policy "${APPROVER:-llm-reviewer}" --spec "$TASK" &

# 3. One planner and N workers, all headless Claude Code
$CC -p "$(cat "$TASK") Plan this as a Tandem epic, then wait for approval." > "$OUT/planner.jsonl" &
pids=($!)
for i in $(seq 1 "$N"); do
  $CC -p "You are Tandem worker $i. queue_wait for approved work, then loop queue_next →
         task_claim → build → task_complete. Stop when the epic is done." > "$OUT/worker-$i.jsonl" &
  pids+=($!)
done
wait "${pids[@]}"                                    # runner enforces the time and token budget
eval/harness.yaml 
name: my-claude-setup
source: upload: [CLAUDE.md, .claude/, .mcp.json]   # copied into each workspace
install: npm i -g @anthropic-ai/claude-code
run: claude -p "$(cat {task})" --dangerously-skip-permissions --output-format stream-json --verbose
vary:
  SUBAGENTS: [off, on]        # off = .claude/agents removed for that setup
collect: [out/*.jsonl]
secrets: [ANTHROPIC_API_KEY]

No run.sh needed. Turns, tokens, cost and duration all come from the stream-json transcript.

eval/harness.yaml 
name: some-agent
source: github.com/someone/some-agent@v1.4
install: pip install -e .
run: some-agent --task {task} --cwd {workspace}
vary:
  MODEL: [claude-sonnet-5-5, gpt-x, glm-x]   # same harness, different models
collect: [logs/]

Human in the loop

How the approval gate works with no human

Tandem's local mode (TANDEM_AUTH=none) decides who's human with a cookie it sets when the board's page loads. Agents never load that page, so they stay agents (apps/api/internal/api/local.go). The stand-in loads the page once, gets the cookie, and then calls the same approve and reject endpoints the board's buttons use. That means you can demo it without changing Tandem.

Fix after the hackathonWith that shortcut, the stand-in's decisions are recorded as human, which breaks Tandem's own rule that only a real person earns that stamp. The proper version is a sim:<policy> stamp, allowed only on canvases marked as eval canvases, plus task.proposed and epic.proposed webhooks so the stand-in doesn't have to poll.
Scope

What to build: all software in the pitch, three proofs in the demo

Is what I built better than what it competes with, by how much, and why?

The vision is any software through one entry: the agent-built eval kit. The hackathon demo proves that entry works on three very different projects, all of which run headless on Naïve computers. The rule that makes it trustworthy is the same for all three: no speed number without a correctness gate.

In: the demo

  • Harness: Tandem against plain Claude Code and subagents (the app mock above)
  • Software: a headless head-to-head, such as a CLI or library against its competitors, with a planted cheater that drops work and gets caught
  • Scan: connect GitHub, get a proposed benchmark for every repo, run two of them
  • The five proof checks, run automatically for every kit
  • A written "why" for every result: where it wins, where it loses, what explains it

Out: say it's on the roadmap

  • GUI rendering speed (a terminal's frame rate, games), which needs a real display and GPU. Parsing throughput can run headless
  • Mobile apps and anything needing physical hardware or robots
  • Hosting model weights to test models against their weight class
  • Accounts, billing UI, team features

Check at the event

Open questions

  1. Can a Naïve computer keep background processes running (the Tandem server plus N claude processes) for 20–40 minutes?
  2. How many computers can fork from one snapshot at once, and what's the concurrency cap?
  3. How do you pass ANTHROPIC_API_KEY safely? Plain environment variables until their vault feature ships.
  4. Does Tandem's approve endpoint accept the local cookie from a script exactly as it does from the board? Worth a five-minute test on your laptop before the event.
  5. GUI software needs a display. Can a Naïve computer run a virtual display for headless parsing benchmarks? Real frame-rate tests will need GPU machines later.
